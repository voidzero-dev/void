# Server Components

From the workspace root, run `vp run --filter ./playground/server-components dev`
and open `/`. The grid links to each live demo, and source links are available
in the grid and on the example pages. In dev, they open the local checkout in
VS Code. Built previews and deployments link to the `server-components` branch
on GitHub.

## Try it with JavaScript disabled

- Open `/weather`, pick a Cloudflare office hub, and press **Show**. The async
  page reads `?location=` from the request context and fetches the city's
  temperature from Open-Meteo without a loader or API key.
- Submit the form on `/greeting`. The loader reads the name from the URL query.
  Enter `<reader>` as the name to see it rendered as text.
- Try `/async-context?greeting=Welcome` to see the async layout pass a greeting
  through `void/jsx` context, and `/css` to see the responsive grid without the
  root layout.
- Submit `/preview` to see a plain POST update both the draft heading and the
  browser tab. The draft lives only for the request and resets on a fresh GET.
- View source on `/posts/42`. The deferred loader props are already present in
  the heading, title, and meta description. There is no loading placeholder or
  hydration script.
- Compare `/posts` (root and nested layouts), `/posts/layout-example` (root and
  named layout), `/exclusive-layout` (named layout only), and `/about` (no layout).
- Open `/custom-layout` to see a directory layout add its own header and
  footer and read the current request path.
- Follow `/posts/latest` to see a loader redirect. Compare `/posts/missing`
  (a loader-triggered 404 that keeps the root and posts layouts) with `/missing`
  (an unmatched route that keeps only the root layout).

## Build and prerender

Build for Cloudflare Workers with `vp run --filter ./playground/server-components build`
and run `vp run --filter ./playground/server-components preview` to preview.

To deploy the `void-server-components` Worker with the globally installed Cloudflare CLI,
run from the workspace root:

```sh
cd playground/server-components
cf deploy --dry-run
cf deploy
```

With the default server output, the post page opts into deploy-time edge
prerendering with `prerender = true`. To inspect generated HTML locally, add
`target: 'node'` and `output: 'static'` to `void.config.ts`, then build again:

- `dist/client/posts/42.html` and `dist/client/posts/43.html` are generated by
  `getPrerenderPaths()`. Their resolved metadata and body are in the files.
- `dist/client/about.html`, `dist/client/preview.html`, and `dist/client/weather.html` are absent because
  those pages opt out. Static-only hosting cannot run the greeting loader for
  new query strings or accept draft POSTs. Restore the server config for the
  interactive tour.

## Supported file shapes and limits

`pages/about.server.tsx` default-exports its view. In an adapter app,
`pages/about.tsx` can instead own the view while `pages/about.server.ts` exports
only handlers such as `loader` or `action`. Don't give both files a view for the
same URL. A named `Page` export is not a server view, and `ssr = false` is not
supported on one.

Use `_not-found.server.tsx` for a server 404 boundary, not `_error.server.tsx`.
Keep client hooks and browser event handlers in hydrated adapter pages. Shared
presentational JSX can work on both sides; the
[mixed-adapter test](../../packages/void/test/integration/server-components.test.ts)
shows the difference.

`InferServerProps` unwraps top-level deferred fields. Use a named group when
several fields come from one resolver; the
[protocol test](../../packages/void/test/unit/pages-protocol.test.ts) checks
that the resolver runs once and that `head()` and the page get the same
resolved props on GET and POST.
